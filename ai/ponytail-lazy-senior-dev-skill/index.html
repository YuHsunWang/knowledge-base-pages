    Ponytail：讓 Coding Agent 少寫一點的 Claude Code Plugin¶

    整理自 DietrichGebert/ponytail 4.10.0 的 README、skill 原檔與 benchmark 報告，2026-10-03。

    ⚠️ 文中的節省比例是作者的 benchmark，本庫沒有重跑。

    一句話¶

    叫 agent 做一個日期選擇器，它會裝 flatpickr、包一層元件、加樣式表，再開始討論時區。Ponytail 會讓它回你一行：

    <!-- ponytail: browser has one -->
<input type="date">

    這是一個 Claude Code plugin，裝了之後每個 session 都自動開著，逼 agent 選最省事、還能用的寫法。名字來自每家公司都有的那位綁馬尾資深工程師：你給他看五十行，他不說話，換成一行。

    七層階梯¶

    寫程式之前，agent 由上往下問，停在第一個成立的那層：

    1. 這東西需要存在嗎？    → 不需要就跳過（YAGNI）
2. 這個 codebase 裡有了嗎？→ 重用，別重寫
3. 標準函式庫做得到嗎？   → 用它
4. 平台原生功能有嗎？     → 用它（<input type="date">、CSS、DB 約束）
5. 已經裝的套件能解嗎？   → 用它，別為幾行程式加新依賴
6. 一行寫得完嗎？         → 一行
7. 都不行才寫最少能動的版本

    階梯有兩條但書，我覺得是它跟「叫模型寫短一點」最大的差別：

    • 先讀懂再偷懶。 階梯在理解問題之後才跑。改 bug 前要先 grep 所有呼叫端，修在共用函式，不是只修工單點名的那條路。
    • 有些東西不准省。 信任邊界的輸入驗證、防止資料遺失的錯誤處理、安全措施、無障礙基本功，一律保留。

    刻意抄的捷徑要留 ponytail: 註解，寫清楚天花板在哪、之後怎麼升級。/ponytail-debt 會把這些註解收成一張清單。

    怎麼一直開著¶

    Plugin 掛了三個 hook（Claude Code 在特定時機自動執行的指令）：

    時機 做什麼
    SessionStart（開新、resume、/clear、compact） 注入 ponytail 規則
    SubagentStart subagent 也注入
    UserPromptSubmit 追蹤你有沒有切換強度

    hook 用 Node.js 跑，node 要在 PATH 上。找不到的話 skill 本身照樣能叫，只是不會自動開。

    強度有三段，用 /ponytail lite|full|ultra 切，預設 full：

    強度 行為
    lite 照你要的做，順便用一行提更省的做法，讓你選
    full 階梯強制執行
    ultra 先刪再加，交出一行版本，同時質疑需求本身

    說「stop ponytail」或「normal mode」就關掉。

    其他指令¶

    指令 用途
    /ponytail-review 只抓過度設計的 code review：每條寫位置、刪什麼、用什麼取代
    /ponytail-audit 同上，掃整個 repo
    /ponytail-debt 收集所有 ponytail: 註解
    /ponytail-gain 顯示 benchmark 成績

    /ponytail-review 不找 bug，只找可以刪的東西，要跟一般 review 搭著用。

    Benchmark（作者測的）¶

    作者讓無頭模式的 Claude Code 改一個真的 FastAPI + React 專案（tiangolo 的 full-stack-fastapi-template），12 張功能工單，用留下的 git diff 評分。模型是 Haiku 4.5，每組跑 4 次。

    對照沒裝 skill 程式行數 token 成本 時間 安全檢查
    ponytail -54% -22% -20% -27% 100%
    caveman -20% +7% +3% +2% 100%
    「YAGNI＋一行解」提示詞 -33% -14% -21% -30% 95%

    差距集中在有過度設計陷阱的題目。日期選擇器從 404 行變 23 行，顏色選擇器從 287 行變 23 行，因為它改用原生 <input>。本來就很精簡的題目，幾乎沒差。

    報告自己列了限制：

    • 只測 Haiku 4.5，大模型的差距可能變小也可能變大
    • 安全檢查只是底線：6 題、確定性檢查，只看有沒有拿掉已知的防護，不代表程式碼安全
    • n=4，前端題的行數每次跑差很多（同一個自製元件 300–570 行）

    README 首頁寫的 80–94%，是更早的單輪生成測試。有人在 issue #126 指出，沒裝 skill 的模型會在答案裡塞說明文字和選項，所以那個落差有一部分是假的。作者把 agentic 數字當成修正後的版本。這段處理我覺得很老實。

    作者也提醒：省成本是附帶效果。會花 thinking token 反覆推敲階梯的推理模型，成本可能反而上升，GPT-5.5 就是這樣。

    跟 Caveman 的差別¶

    本庫寫過 Caveman。兩個都號稱省 token，打的地方不同：

    • Caveman 壓的是講話：拿掉客套和贅字，程式碼原樣保留。
    • Ponytail 壓的是程式碼本身：一開始就不寫不需要的東西。

    上面的 benchmark 裡 caveman 被當成對照組。在 agentic 任務上，它的 token 和成本反而微增。

    我的用法¶

    我一直開著 full。我的全域規則本來就有「最少程式碼、不加沒人要的抽象」這一條。Ponytail 把它變成一張可以照著走的階梯，加上一張「不准省」的清單，比一句原則好執行。

    它只管寫什麼程式碼，不管怎麼說話。回報格式還是看 Claude Code 的 output style。

    安裝¶

    在 Claude Code 裡分兩次送出：

    /plugin marketplace add DietrichGebert/ponytail

    /plugin install ponytail@ponytail

    README 特別註明兩行要分開送，一起送會裝不起來。Codex、Cursor、Gemini CLI 等也有對應安裝方式，見 repo。
