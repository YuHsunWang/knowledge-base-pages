    Claude Code Code Review Coding Agent

    Claude Code 團隊怎麼做 Code Review：七層檢查與看風險決定要幾個人¶

    整理自 Anthropic〈How the Claude Code team does code review〉，2026-10-15 發布。資料基準 2026-10。

    ⚠️ 文中數字都是 Anthropic 內部的數據，本庫沒有辦法重現。

    摘要¶

    Claude Code 大約九成的程式碼是 Claude 自己寫的。改動量一多，人一行一行看已經不可能。這篇講他們怎麼處理。

    核心是換一個問題。他們不再問「有沒有人讀過這段程式」，改問：

    這次改動可能壞在哪？該由哪一道檢查（自動或人工）抓到？

    照這個問題重新設計之後，2026 年 6 月到 9 月，Claude Code 合併的 PR 數量多了一倍以上，需要 revert（退回）的比例反而少了四成以上。

    做法有四個重點：

    1. 審查一直在跑：像打字時的拼字檢查，不再是最後一道關卡。人看到 PR 之前，Claude 通常已經審過、修過至少一次。
    2. 七層檢查疊起來：每一層都會漏，但很少東西能穿過全部。最後一層是快速退回。
    3. 看風險決定要幾個人核准：低風險不用人，中風險一人，高風險兩人。由改動本身決定，不看作者是誰。
    4. 審查員本身也被測：過去的事故做成 eval（考題），每天考一次；審查輪數設上限，避免 AI 寫、AI 審互相卡住。

    問題背景：改動暴增，人的時間不夠¶

    Anthropic 的 monorepo（所有專案放一起的大 repo），每天合併的改動從 2026 年 5 月的約 2,500 個，漲到 9 月的三萬多個。Claude Code 有自己的 repo，但壓力一樣大。

    Code review 原本有兩個工作：

    1. 在上線前找到問題、修掉。
    2. 讓團隊互相了解程式碼。

    這篇主要講第一個，最後才回到第二個。

    他們把人的時間當成最稀缺的資源。人的時間有兩種花法：花在審查，跟花在修爛程式碼弄壞的東西。只砍第一種沒用，時間會跑去第二種。

    所以目標寫得很具體：Claude Code 各 repo（CLI、桌面版、網頁版、手機 app）大部分 PR 合併時，最多只要一個人參與，這個人可以就是作者，而且 revert 和事故不能變多。

    他們追蹤這些數字：

    類別 指標
    人的時間 每個 PR 要幾個人核准（中位數、第 95 百分位）、人留了幾則意見、PR 等人等了多久
    護欄 revert 率、事故率。這兩個上升，代表時間沒省到，只是搬去別的地方

    七層檢查¶

    一個改動從工程師電腦（或 Slack 裡的 Claude session）出發，到使用者手上，要經過下面幾層。

    第 1 層：給別人看之前，自己先驗證¶

    大部分審查現在發生在 PR 開之前。

    • 給 Claude 可以跑的東西：測試、build、或拿設計稿比對的截圖。要它貼出跑的結果，不能只說「做好了」。
    • 再開一個 subagent（子代理），用全新的 context 審一次 diff。
    • 很多人開 PR 前還會跑幾個內部 skill：一個抓 bug、一個把 diff 簡化、一個做端到端的行為檢查。UI 改動另外對照設計規範。

    Claude Code 的作者 Boris Cherny 說，讓 Claude 有辦法驗證自己的成果，「大概是最重要的一件事」，他估計成果會好兩到三倍。驗證的方式看領域而定，可能只是跑一行 bash，也可能是在瀏覽器或手機模擬器裡實際操作。

    同一個問題一直被抓到，就從源頭修。 修在 skill 裡、加 lint 規則，或改說明檔：

    • CLAUDE.md：告訴 Claude 這個專案是什麼——技術堆疊、慣例、目標、不做什麼。每次審查都會讀它，所以大型專案要寫短，細節連到其他文件。審查員也會抓「違反裡面慣例」和「讓裡面某一行過時」的改動。
    • REVIEW.md：由 code owner（負責那塊程式的人）寫，告訴審查員在他們的範圍裡什麼最重要。他們會另外檢查審查員有沒有真的照做。

    好的 REVIEW.md 有這些特徵：

    • 很短。
    • 寫出在這個 repo 裡「壞掉」長什麼樣子。例如文件壞掉是「它說謊」，設定檔壞掉是「它送錯地方」。
    • 限制小意見（nit）的數量。
    • 列出不用看的路徑。
    • 要求附上檔案和行號當證據，不准只看名稱就猜。
    • 要求摘要開頭先給數量；沒東西要修時，直接說沒有。

    第 2 層：每個 PR 都有 AI 審查¶

    人看之前，每個 PR 都先被 Claude 審一次。它拿 diff 對照整個 repo 和 PR 說明的意圖，問三件事：有沒有解決問題？跟系統合不合？會不會弄壞別的東西？如果是修 bug，它會去找根本原因。

    公開版叫 Code Review for Claude Code，Team 和 Enterprise 方案可以用。本機的 /code-review 是輕量版。

    研究預覽版上線後，內部 PR 收到實質審查意見的比例，從 16% 升到 54%。超過 1,000 行的 PR 大多會被抓到東西，小 PR 大多乾淨過關。管理員可以把每個 repo 設成 Quick、Standard 或 Deep 三種深度。漏掉一個 bug 的代價，比多審的時間貴的地方，才值得開 Deep。

    意見先給其他 agent 驗證，才給人看：

    1. 好幾個 agent 同時找 bug。
    2. 另一組 agent 對每條發現投票，夠多個同意是真的才貼出來。
    3. 只講風格、診斷訊息、清理的意見直接丟掉。這些過濾規則他們在自己的 PR 上做過 A/B 測試才留下來。
    4. 剩下的依嚴重度排序，標成 Important、Nit 或 Pre-existing（本來就有的問題）。最後一種是為了不讓「這個 PR 沒造成的 bug」看起來像作者的錯。

    每條意見都要回應。 不是修掉，就是寫理由關掉。常常 agent 晚上就把修正做完，作者早上回來時 PR 已經又跑完一輪。

    第 3 層：可以擋住合併的安全審查¶

    安全有獨立的自動審查。bug 審查或安全審查只要還有一條沒處理，PR 就不能合併。誤報（false positive）的處理方式一樣：寫一句理由關掉。之後的 commit 如果修好了，那條會自己消失。

    想自己用，可以裝開源的 security review GitHub Action，或用 /security-review 指令。

    第 4 層：會擋人的自動檢查¶

    就是常見的那些：lint、型別檢查、各平台的測試、build。一個普通的 CLI PR，在有人看之前可能已經跑了幾十項檢查。

    PR 範本會問：這個改動怎麼測的？要怎麼退回？Claude 可以幫忙填，但要由提出這個改動的人簽名負責。

    第 5 層：看風險決定要幾個人核准¶

    改文件跟改自動更新程式，風險不一樣，審法也不一樣。

    風險 例子 要幾個人核准
    低 文件、文案、只給內部用的功能、藏在開關後面的新增功能 不用人，自動審查和安全檢查都綠就好
    中 一般產品改動；碰到敏感區域，例如快取、自動更新程式、system prompt 一個人
    高 風險最高的程式，加上少數規定一定要兩個人的路徑 兩個人

    幾條配套規則：

    • 由改動決定等級，不看作者。 一個分類器讀改動、決定風險等級。另一個分類器再問：就算等級說不用，這個改動是不是還是需要多一個人？code owner 標成敏感的路徑、任何 CI workflow 檔，一定要有人。
    • 只有信任名單上的作者能走輕量路線。 名單上大多是負責那個 repo 的團隊。其他人都要第二個人核准。
    • agent 的核准不算人的核准。 自動審查可以放行低風險改動，但不能補上「要一個人」的那個位置。
    • 誰叫 agent 寫的，誰就要負責。 agent 寫的 PR，指揮它的人算一個必要審查者，跟他自己打字寫的一樣。
    • 核准只對某一個 commit 有效。 之後如果有系統沒辦法擔保的新 commit 進來，例如 agent 推上來的、或有人手動解衝突的 merge，就要重新核准。

    第 6 層：merge queue、開關、慢慢上線¶

    • merge queue（合併排隊）：每個 PR 合併前，會套在最新的 main 上把檢查再跑一次。這樣兩個各自通過的 PR，不會合在一起把 main 弄壞。
    • feature flag（功能開關）：新功能通常先藏在開關後面，只給 Anthropic 員工用。員工用得很兇，常常比使用者先發現退步。
    • 分階段發布：公開版本先進 latest 頻道，stable 頻道晚一步跟上。

    第 7 層：快速發現、快速退回¶

    還是會有錯漏過去，所以最後一層是快點抓到。

    • 開關不用重新部署就能關。
    • Claude Code 有每週輪班的 on-call（值班）。
    • 事故檢討時會問：這個問題應該由哪一層抓到？

    他們也承認還缺一塊：目前沒有「revert 或事故數字一上升，就自動收緊核准規則」的斷路器（circuit breaker）。工程師希望先有這個，才讓更多程式碼走「零人工合併」。

    一位同事的說法：放慢速度確實會降低錯誤率，但主要是因為什麼事都做得比較少。他們寧可練習更快發現、更快修好。

    怎麼讓審查員變好¶

    事故變成考題¶

    1. 團隊收集過去造成事故的 PR，連同後續的修正和 revert。
    2. 請熟悉那段程式的工程師確認每個 bug 真的存在、在哪裡。
    3. 每有新事故就加一題。
    4. 審查員的 prompt、工具或模型一改，就拿整份考題重考。分數有升就留，沒升就丟。

    這份考題每天跑一次。

    雜訊怎麼量¶

    只要不在乎誤報，要抓到更多 bug 很簡單。所以要另外量雜訊。

    • 審查員留的每一則意見，依 PR 上的人怎麼回應來分類：修了、說它錯了、說這是故意的、覺得不重要。
    • 拿已知乾淨的 PR 給審查員審，數它多常報出「會讓人做出有害修改」的東西。

    他們寫下來的優先順序是：先抓到真的 bug，其次才是減少審查輪數。

    為什麼雜訊在 AI 作者身上更貴

    人看到一則小意見，幾秒就能跳過。 AI 作者會乖乖去改，於是多一個 commit，再觸發一輪審查。 同樣一則雜訊，對人是幾秒，對 AI 是一整輪。

    審查一定要收斂¶

    AI 作者和 AI 審查員可以互相找事做，永遠停不下來。有一個 CLI 的 PR，晚上自己來回審、改了五十幾輪，最後是作者手動叫停的。

    他們對審查員一直抓的東西跑 git blame，發現大約 59% 是審查員第一輪就已經在的舊程式碼。審查員很少找到新 bug，只是每一輪多挖出幾個舊的。

    這個問題有一部分是他們自己造成的：大家習慣預設跑好幾輪，因為每一輪都會多抓到一點東西。高風險的改動值得這樣做，但不是每個 PR 都值得。

    現在他們把「幾輪才過」跟「抓到多少 bug」一起追蹤，並改了重審規則：

    • 輪數上限：三輪之後，審查員會請作者退一步，重新想做法。
    • 只審新的 diff：前幾輪過後，只看新改的部分。
    • 標出整類 bug：讓作者一次修掉所有同類問題，只修一行不算數。
    • 不重複：已經貼過的意見不再貼。

    另外，審查 agent 每天晚上會掃一遍現有程式碼，把舊 bug 在它跑去別的地方之前抓出來。

    改完之後的內部數字：

    指標 改之前 改之後
    一輪審查＋修正就通過 65% 78%
    要五輪以上 8.9% 1.5%
    平均幾輪才過 2.08 1.32

    人還留在哪裡¶

    叫一位資深工程師從專注的工作中停下來，去抓一個例行錯誤，成本遠高於一次自動審查。所以人的工作從「讀每個 diff」，換成機器不擅長的五種決定：

    1. 這個該不該做？ 方向、品味、範圍。有個團隊宣布審查瓶頸已經解決，但還是保留人工審查給「團隊外的人送來的改動」，好讓有人問一句「我們真的要做這個嗎？」
    2. 高風險程式：付款、自動更新程式、CI workflow。
    3. 架構：會變成別人照抄範本的那種。
    4. 讀證據：測試輸出、跑了什麼指令和它回傳什麼、截圖、審查員的意見。如果你說不出這些檢查會漏掉什麼，就該要求認真審，別隨手按核准。
    5. 為結果負責：不管是誰打的字，每個上線的改動都有一個人負責。

    機器幫忙讀，那大家怎麼認識程式碼？¶

    這是 code review 的第二個工作：讓大家了解程式碼。以前靠讀同事的 diff 學到東西改了什麼、各部分怎麼接。

    他們沒有正式流程。團隊裡沒人腦中有整個 Claude Code 的完整模型，他們也覺得不需要。想了解某一塊時，就請 Claude 針對那一小塊寫一份說明。幾分鐘就好，而且反映的是今天的程式碼。有些人更進一步，請 Claude 做一個小 artifact，把那段程式畫出來，用自己喜歡的方式學。

    比起一行一行讀小 diff，這更划算。改一行文案的 diff 幾乎學不到東西；你要改的那個模組的說明，可以學到很多。他們預設在公開的 Slack 頻道工作，也有幫助：別人在做什麼，做的當下就看得到。

    「你合的，你負責」¶

    如果你合併了小或中型的改動，之後出問題，團隊慣例是通常由你修。下面幾件事讓這條規則不會變成壞事：

    • 改動很小：好審、好除錯、好退回。
    • 什麼都能退回：開關、revert、分階段發布，大部分錯誤幾分鐘就能撤掉。
    • 影響範圍決定門檻：越貴的程式碼，越多人、越多檢查。
    • 退步很快浮現：靠遙測（telemetry）和內部使用。
    • 不是追究責任：由你修是因為你最了解狀況；事故檢討看的是系統。

    責任也是共享的。很多人在公開頻道工作，任何人都能看到別人在做什麼、接手一條討論，或叫一個 Claude 去補缺口。

    方向要改，就早點說¶

    agent 讓開始一件事變得很便宜，所以有些工作本來就不該合併。通常是頻道裡有人問「為什麼」、指出之前的決定、或提一條更簡單的路，作者就把 PR 關掉或改方向。

    程式寫得快，關掉 PR 也不覺得可惜。訣竅是：在討論串裡早點提出不同方向，不要等 PR 做完才留一則擋人的意見。

    照著做的清單¶

    原文最後給了一份清單，大部分工具現在都有。

    開 PR 之前

    • 給 agent 可以跑的檢查，寫在一份短的 CLAUDE.md 裡；加上自動跑 formatter 和 linter 的 hook。
    • 在本機跑 /code-review 和 /security-review，或開一個全新 context 的 subagent 審查。
    • 加一份 REVIEW.md，把一直重複的審查意見搬進去。

    每個 PR

    • CI 必過。PR 範本加上「測試方式」「風險」「怎麼退回」三欄。
    • 先在一個 repo 試 AI 審查員（Code Review for Claude Code，或 Claude Code GitHub Action），調幾週 REVIEW.md 再擴大。
    • 加自動安全審查，規定所有討論串都要處理完才能合併。
    • 審查深度跟著風險走：例行改動快速過，漏一個 bug 很貴的地方審深一點。
    • 限制審查輪數；前幾輪過後只審新的 diff。

    核准

    • 把風險等級寫下來，由改動決定、不看作者。先嚴後鬆，有證據才放寬。
    • 輕量核准路線只給信任的作者。
    • 用 CODEOWNERS 和 branch protection，讓認證、付款、CI 與發布 workflow、安裝程式永遠需要人。
    • 機器人的核准不能取代必要的人工核准；有新 commit 就撤銷舊核准。

    合併與之後

    • 用 merge queue、功能開關、先內部使用、分階段發布、一步退回。
    • 把事故和 revert 做成 eval；審查員的 prompt、工具或模型一改就重考。
    • 量人的時間，用 revert 率和事故率當護欄。

    往哪裡走¶

    Code Review 產品公告說，核准 PR 仍然是人的決定；產品只貼意見，不給核准。Anthropic 自己的 repo 走得更遠：讓 code owner 決定哪些低風險改動可以只靠自動檢查合併，而且這條線還在移動。

    審查漏掉東西時，他們問的是：模型當時缺了什麼資訊？然後把修正寫進 CLAUDE.md、skill，或加一個新檢查。

    延伸思考¶

    • 這套做法很依賴「什麼都能快速退回」。如果你的系統改動退不回來（例如資料庫 migration、對外發出的訊息），第 5 層的風險分級要比原文更嚴。
    • 「事故變考題」不需要很大的團隊。個人專案修過的 bug、被退回的 PR，一樣可以收成一組固定案例，用來比較換模型或換 prompt 之後審查員有沒有變好。
    • 審查輪數上限對個人使用 AI 審查也適用：同一個 PR 讓 AI 審到第三輪還在出新意見，通常代表該回頭檢查做法，別再繼續修。
